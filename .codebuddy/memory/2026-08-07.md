## 验证 PIX Global ID 是否跨队列唯一（结论：成立，带4 条限定）

新增 `tests/verify_global_id_uniqueness.py`（24 项检查，在 Tiled + verify 两个会话上全过）。

### 实测事实（Tiled.wpix / verify=NoTiled.wpix，PIX 2603.25）
- C++ 导出 `// GlobalId = N` 共 5539 个，**零重复**，range 2..6040。
- 2786 个 action **全部**有 global_id 且唯一；queue_id 只覆盖 2696（缺 90 个 async compute）。
- 跨队列决定性证据：3D Queue gid 23..6035、Compute Queue gid **4690..5257**——区间嵌套交错但**零碰撞**。若是每队列独立计数器，compute 必然从 0 开始并大面积撞车。
- 90 个 compute action 的 gid 在单队列 CSV 里**全部不存在**（与全局编号一致）。
- gid 随 draw_index **单调递增**，0 个逆序。
- 端到端：`pixtool save-resource --global-id=` 无队列参数。gid=23（3D 队列）exit 0；gid=4690（compute 队列，CSV 无此行）PIX 打印 "Requesting active resources for **global event** 4690" 后仅因compute dispatch 无 RTV 报PIXTOOL9；gid=106042（不存在）报 PIXTOOL99999 + 崩栈。→跨队列 id 被 PIX 正常解析。

### 必须限定的4 点（推翻现有代码注释）
1. **不连续**：1..6042 中有 170 个 id 两个来源都没有，不能做 range 扫描。
2. **不止 action**：query1304 / barrier 426 / clear 338 / copy 234 / sync 189 也有 gid。代码里 `capture.py:664` 和 `model.py:681` 写的"Global ID only appears on actions"是**错的**。
3. **marker 无 gid**：564 个 marker 全部为 None → `queue_id` 不能删，pass 标记行只能靠它。
4. **144 个 CSV action行无对应 C++ action**：全部是 ExecuteIndirect 展开出的子 dispatch（parent 均为 ExecuteIndirect），`resolve_draw(global_id=)` 对它们会返回 None，需专门文案。

### id 空间重叠（改造的关键约束）
queue_id 空间 0..22154（=行号），global_id 空间 1..6042，**5424 个整数在两个空间都合法**；且 0 个 action 满足 queue_id==global_id → 混用永远错、且无法按数值自动判别，只能靠显式命名参数 + 交叉提示。

## 追加：按两个具体验收目标重订改造计划

用户目标：`Global ID=5099 → pass "CompactTraces WaveOps:1"`；`Global ID=3893 (dispatch) → pass "TileClassificationMark"`。
新增 `tests/acceptance_global_id_selector.py`（先写后实现，当前 **11/22 红**）。

### 两个目标失败原因完全不同
- **3893**：3D 队列 Dispatch，`find_pass_by_event(global_id=3893)` **今天就返回** pass 140 TileClassificationMark，`resolve_draw(global_id=)` 也已返回 draw 2475。**只差工具层不收这个参数**。
- **5099**：**导出和 CSV 里都不存在**（是 221 个空洞之一）。实测它是 gid=5098 那个 ExecuteIndirect（CommandLists_001.cpp:12741, cl=3847, draw_index=2671, pass="CompactTraces WaveOps:1"）被 PIX 展开出的子 Dispatch。证据：CSV 里144 个 ExecuteIndirect 的子行，`child_gid - parent_gid` 分布 **{1: 144}**，无例外；且 5099 恰好满足 gid-1 是导出里的 ExecuteIndirect（43 个空洞属于这一类）。该 pass 在 **Compute Queue**，qid=None。

### 新查明的阻塞点
`Capture.find_pass_by_event`走 `resolve_event` → **只查 CSV**，因此对全部 **90 个无queue_id 的 action一律返回 None**（实测 resolved=2696/ unresolved=90）。必须加一条 draw→marker_path→pass 的非 CSV 路径。

### 两个必须堵死的陷阱（实测反证）
1. **区间包含法不可用**：5099 同时落在 3 个 pass 的 gid 区间内（LumenReflections 4680..5373、ClearBuffer(...) 5094..5123、CompactTraces WaveOps:1 5098..5127），后两者宽度**都是 29**，"取最窄"也无法决断。根因：`passes` 按 marker_path 分组，UE5 同名pass 复现导致 draw 不连续（pass319 只拥有 draw 2670/2675，pass320 只拥有 2671/2676，二者交错），区间互相吞并。全导出 343 个 gid 落在 2~5 个 pass 区间内。
2. **"最近前一个 action"不可作通用回退**：221 个空洞里只有 43 个前一位是 ExecuteIndirect，其余 178 个前一位是 WriteBufferImmediate(87)/DiscardResource(25)/sync(19)/EndQuery(17)/ResourceBarrier(13)/Dispatch(6)/CopyBufferRegion(5)，硬回退会对这 178 个自信地答错。

### 导出 gid 全量构成（阶段 1 索引的依据）
5539 个 gid / 11 种 API：DrawIndexedInstanced 2373、**WriteBufferImmediate 1572**、DiscardResource 333、ResourceBarrier 299、Dispatch 208、ExecuteIndirect 187、CopyBufferRegion 112、EndQuery 73、BeginQuery 62、DrawInstanced 18、未跟到调用 302。→ 只索引 DrawCall 会丢 2753 个 gid。

### 交叉提示的最强动机（同一整数两义）
`3893` 作 global_id 是目标 Dispatch；作 queue_id 命中第 3893 行 `IASetVertexBuffers`。README:222-223 现在正拿 3893 当"危险误用"的例子。
